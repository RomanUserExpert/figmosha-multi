# Component Builder

Главная ошибка при сборке компонента через API — построить технически корректный узел, который не похож ни на что в файле. Поэтому: **сначала разведка, потом стройка.**


## Перед первой командой

Если открыт больше чем один Figma-файл, команда без адреса вернёт 409 со
списком — это не сбой, а вопрос «в каком файле». Выбирать за пользователя
нельзя: правка уйдёт в чужой файл молча. Спросить и закрепить на сессию:

```powershell
$env:FIGMOSHA_SESSION = "<имя файла или sid>"   # разово: --session <имя>
```

Что подключено — `python figmosha.py sessions`.

## Шаг 1 — найти образцы

Взять 2–3 существующих компонента из той же группы (другие формы, другая навигация — не случайные):

```bash
python figmosha.py find <page-or-frame-id> type=COMPONENT_SET
```

Затем снять с них конвенции:

```bash
python figmosha.py exec --file .claude/skills/component-builder/scripts/conventions.js \
  --set 'REFS=["185:21883","185:22010"]'
```

Скрипт вернёт: имена вариантов и разбор на `Property=Value`, `variantGroupProperties`, componentPropertyDefinitions, настройки auto-layout, какие переменные к чему привязаны, имена слоёв.

**Это вход в проектирование, а не формальность.** Дальше повторяется то, что оттуда видно.

## Шаг 2 — проверить, нет ли уже такого

```bash
python figmosha.py find <root-id> name~Button
```

Близкий компонент существует → предложить расширить его новым вариантом вместо создания дубля. Второй компонент под другим именем, делающий то же самое, — это долг, а не результат.

## Шаг 3 — согласовать матрицу вариантов

Выписать предполагаемую матрицу (states × sizes × emphases) **и показать пользователю до сборки**. Размер матрицы = произведение, оно растёт быстро: 4 состояния × 3 размера × 2 типа = 24 варианта.

Если в матрице нет состояния, которое есть у соседей (hover / focus / disabled / error / loading) — спросить, а не выкинуть молча.

## Шаг 4 — сборка, два этапа

Правило из `CLAUDE.md`, здесь оно обязательно:

**Этап A — структура с хардкодом.** Собрать геометрию и auto-layout, всем слоям дать **осмысленные имена**, по которым этап B их найдёт. Порядок операций (иначе Figma тихо проигнорирует часть):

```js
parent.appendChild(f);        // 1. в дерево
f.layoutMode = "HORIZONTAL";  // 2. layoutMode
f.resize(120, 40);            // 3. размер
f.primaryAxisSizingMode = "AUTO";  // 4. режимы
f.itemSpacing = 8;            // 5. спейсинг/паддинги
```

Проверить этап A отдельно: `python figmosha.py tree <id>`.

**Этап B — привязка переменных.** Обойти по именам и связать:

```js
await h.bF(h.findByName(root, "Bg"), 0, bgVar);      // fill
await h.bS(h.findByName(root, "Bg"), 0, borderVar);  // stroke
await h.bN(h.findByName(root, "Bg"), "topLeftRadius", radiusVar);
await h.bN(root, "itemSpacing", spacingVar);
```

Существующие переменные брать так (не угадывать имена и id):

```bash
python figmosha.py vars                 # карта коллекций: что вообще есть
python figmosha.py vars color/bg        # значения по режимам
python figmosha.py vars --type COLOR
```

Локальных нет — файл потребляет библиотеку: `python figmosha.py vars --library <фильтр>`
вернёт ключи для `h.importVar(key)`.

## Шаг 5 — свойства и combineAsVariants

Свойства регистрировать так же, как у соседей: имя, тип (VARIANT / BOOLEAN / TEXT / INSTANCE_SWAP), набор значений. Имена вариантов — строго в формате файла, обычно `Property 1=Default, Size=Small`.

```js
const set = figma.combineAsVariants(components, parentFrame);
set.name = "Button";
```

## Шаг 6 — самопроверка перед сдачей

```bash
python figmosha.py exec --file <вернуть таблицу property → token>
```

Отдать пользователю:
- таблицу `Свойство | Слой | Переменная` — чтобы привязку можно было выборочно перепроверить;
- строку «структура/нейминг взяты с: `<имена компонентов-образцов>`»;
- id получившегося component set.

## Guardrails

- **Ни одного сырого значения там, где есть переменная.** Цвет, радиус, спейсинг, тип — всё через токен. Хардкод допустим только на этапе A и обязан исчезнуть на этапе B.
- **Не изобретать нейминг.** Он выводится из шага 1, а не из общих представлений о хорошем.
- **Не создавать дубль** существующего компонента под новым именем.
- Не угадывать матрицу вариантов — согласовать (шаг 3).
- Нет подходящей переменной → сказать «нужен новый токен `<предложение>`» и остановиться на этом месте, а не вписывать hex.
- Проверять результат данными (`tree`, `componentProperties`), не скриншотом.
